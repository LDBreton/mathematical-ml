Lección 08 — Un modelo ajustado, una política guardada y una API

Siga un modelo desde el ajuste y la selección del umbral en validación hasta la evaluación final, el guardado, la carga y una solicitud HTTP. El recorrido principal usa un único artefacto desde el entrenamiento en el cuaderno hasta la inferencia por API. El seguimiento con MLflow y un proceso de servidor independiente son extensiones opcionales. El cuaderno usa un cliente de prueba en el mismo proceso y no inicia un servidor en segundo plano.

Flujo conceptual de servicio. A cada registro entrante validado se le aplica el mismo preprocesamiento guardado.

1. Qué atraviesa la frontera

Una artefacto es un archivo que contiene el preprocesamiento ajustado, el predictor y los metadatos. Un servidor proceso carga ese archivo en memoria. Una API es una interfaz a la que llama otro programa. Una solicitud HTTP solicitud envía un objeto JSON a un punto de acceso como /predict; la respuesta contiene un código de estado y datos.

La ruta de inferencia es: campos sin procesar → validación del esquema → preprocesamiento guardado → estimación de probabilidad → umbral guardado threshold → respuesta JSON. El escalador, el codificador de categorías y los coeficientes del modelo se aprendieron durante el ajuste. Una solicitud aplica esas cantidades guardadas; no vuelve a invocar fit con ellos.

Etapa del ciclo de vida Entrada Salida Estado que puede aprenderse o elegirse
fit Filas y etiquetas de ajuste Pipeline ajustado Medias y escalas numéricas, niveles de categorías, coeficientes de regresión logística
predict_proba Nuevas filas de variables predictoras Probabilidades de clase No se aprende ningún estado nuevo
Selección de política en validación Etiquetas y probabilidades de validación Umbral Punto de corte según la regla de costes indicada
joblib.dump / joblib.load Pipeline y metadatos / archivo guardado Artefacto / objetos restaurados No se vuelve a ajustar el modelo fit
Solicitud a la API Un registro JSON que cumple el esquema Probabilidad y decisión No se aprende estado nuevo; solo se realiza inferencia

El cliente de prueba local llama al endpoint real de FastAPI sin iniciar un servidor de larga duración. Una respuesta HTTP correcta comprueba el comportamiento del software, pero no demuestra que el modelo esté calibrado ni que sea útil para futuros clientes.

2. Ajustar una vez y elegir una política en validación

Las filas representan escenarios sintéticos independientes de clientes, por lo que esta lección utiliza particiones aleatorias estratificadas para conservar la proporción de la clase positiva en cada partición. Este método corresponde al esquema de muestreo supuesto para estos datos; para datos temporales o agrupados se necesita una partición que respete sus dependencias.

El pipeline aprende la estandarización, la codificación de categorías y los coeficientes logísticos usando solo las filas de ajuste. Una probabilidad no constituye por sí sola una acción. Con los costes ilustrativos $C_{FN}=5$ por no detectar una baja y $C_{FP}=1$ por contactar innecesariamente, un umbral $\tau$ induce la decisión $d=\mathbf 1[p\geq\tau]$ y el coste de validación

$$C(\tau)=C_{FN}\sum_i\mathbf 1[y_i=1,d_i=0]+C_{FP}\sum_i\mathbf 1[y_i=0,d_i=1].$$

Elegimos el mínimo entre 19 umbrales candidatos, de 0,05 a 0,95; si hay empate, se elige el menor umbral. Esta es una decisión empírica para la muestra de validación. El umbral teórico $C_{FP}/(C_{FP}+C_{FN})$ solo se deduce si las probabilidades están calibradas para la población de despliegue y los dos costes indicados son los costes de decisión pertinentes. Conservamos el umbral elegido en validación y congelamos tanto este como el pipeline ajustado. No volvemos a ajustar con las filas de validación, pues cambiaría la función de probabilidad después de seleccionar el umbral.

Python · ejecutar en el cuaderno
X, y = data[FEATURES], data["churn"].astype(int)
X_development, X_test, y_development, y_test = train_test_split(
    X, y, test_size=0.25, random_state=42, stratify=y
)
X_fit, X_validation, y_fit, y_validation = train_test_split(
    X_development, y_development, test_size=0.20, random_state=17, stratify=y_development
)
pipeline = build_pipeline().fit(X_fit, y_fit)
positive_column = list(pipeline.classes_).index(1)
validation_probabilities = pipeline.predict_proba(X_validation)[:, positive_column]
C_FN, C_FP = 5.0, 1.0
validation_rows = []
for cutoff in np.linspace(0.05, 0.95, 19):
    decisions = validation_probabilities >= cutoff
    fn = np.sum((y_validation.to_numpy() == 1) & ~decisions)
    fp = np.sum((y_validation.to_numpy() == 0) & decisions)
    validation_rows.append({"threshold": float(cutoff), "cost": C_FN * fn + C_FP * fp,
                            "alerts": int(decisions.sum())})
validation_table = pd.DataFrame(validation_rows)
selected = validation_table.sort_values(["cost", "threshold"]).iloc[0]
threshold = float(selected.threshold)
print("Validation-selected threshold:", threshold)
display(validation_table)
fig, ax = plt.subplots(figsize=(8, 3))
ax.plot(validation_table.threshold, validation_table.cost, "o-")
ax.scatter([threshold], [selected.cost], color="crimson", zorder=3, label="Selected on validation")
ax.set(xlabel="Threshold", ylabel="Illustrative validation cost", title="Choose the policy before final assessment")
ax.legend()
plt.tight_layout()
plt.show()

Revisar las particiones y el fit ciclo de ajuste

FEATURES fija el orden de columnas que esperan el preprocesamiento y el servicio. La partición externa reserva los datos de prueba; stratify=y conserva las proporciones de clase y random_state hace reproducible la asignación de filas. La partición interna separa las filas de ajuste y validación dentro de los datos de desarrollo. build_pipeline().fit(...) aprende todo el preprocesamiento y los parámetros logísticos usando las filas de ajuste. classes_ identifica la columna de la clase positiva 1, de modo que la extracción de probabilidades no dependa de suponer un orden de columnas. El ciclo aplica cada umbral candidato a las probabilidades de validación y cuenta los falsos negativos y falsos positivos según los costes indicados.

3. Evaluar el pipeline congelado y guardar la misma política

Aplique una sola vez el pipeline y el umbral ya seleccionados a la partición de prueba final. Estas métricas describen ese par congelado; no sirven para elegir otro threshold. El AUC ROC depende del orden de las probabilidades y no del umbral. La precisión, la exhaustividad y el coste ilustrativo sí dependen de él.

El artefacto es un diccionario con dos partes: pipeline contiene las transformaciones y el estimador logístico ajustados; metadata registra el esquema ordenado de variables, los valores de categorías permitidos, la clase positiva, el umbral, las métricas, los tamaños de las particiones, el hash SHA-256 del CSV de origen y las versiones de Python y las bibliotecas. Guardar juntos el modelo y la política conserva el comportamiento previsto para la API. joblib usa serialización de objetos de Python; cargue solo archivos de fuentes confiables y mantenga un entorno de software compatible.

Python · ejecutar en el cuaderno
test_probabilities = pipeline.predict_proba(X_test)[:, positive_column]
test_decisions = test_probabilities >= threshold
metrics = {
    "roc_auc": float(roc_auc_score(y_test, test_probabilities)),
    "precision": float(precision_score(y_test, test_decisions, zero_division=0)),
    "recall": float(recall_score(y_test, test_decisions, zero_division=0)),
    "cost": float(C_FN * np.sum((y_test.to_numpy() == 1) & ~test_decisions)
                  + C_FP * np.sum((y_test.to_numpy() == 0) & test_decisions)),
}
metadata = {
    "artifact_format": 1, "features": FEATURES, "contract_values": CONTRACTS,
    "positive_class": 1, "threshold": threshold, "metrics": metrics,
    "fit_rows": len(X_fit), "validation_rows": len(X_validation), "test_rows": len(X_test),
    "data_sha256": hashlib.sha256(DATA.read_bytes()).hexdigest(),
    "dependency_versions": {"python": platform.python_version(), "scikit_learn": sklearn.__version__,
                            "pandas": pd.__version__, "numpy": np.__version__},
}
artifact = {"pipeline": pipeline, "metadata": metadata}
joblib.dump(artifact, artifact_path)
print("Saved:", artifact_path.name)
display(pd.Series(metrics, name="Final test metrics"))

Puntuar una vez y empaquetar la política

El código calcula las probabilidades de la clase 1 en las filas de prueba intactas y aplica el threshold, luego informa la calidad de ordenamiento y thresholdlas métricas que dependen del umbral. Los metadatos permiten interpretar el artefacto: el esquema y las categorías definen la compatibilidad de entrada; positive_class y threshold definen la regla de acción; las métricas y los tamaños de las particiones describen esta ejecución; data_sha256 identifica los bytes de entrada, y las versiones de dependencias documentan el entorno. joblib.dump serializa en un solo archivo el pipeline ajustado y sus metadatos.

4. Una predicción correcta antes y después de guardar

El cliente ficticio es una prueba del contrato de software, no otra fila de evaluación. Construya una entrada de una fila con los mismos nombres de columnas y llame a predict_proba; luego cargue el artefacto guardado y llame a su pipeline con el mismo registro. La comprobación de igualdad confirma que la serialización conservó la función de probabilidad con precisión numérica. El umbral guardado convierte esa probabilidad en una decisión 0/1.

Python · ejecutar en el cuaderno
customer = {"tenure_months": 8, "monthly_charge": 92.0,
            "support_calls": 4, "contract": "monthly"}
customer_row = pd.DataFrame([customer], columns=FEATURES)
before_saving = float(pipeline.predict_proba(customer_row)[0, positive_column])
loaded = joblib.load(artifact_path)
after_loading = float(loaded["pipeline"].predict_proba(customer_row)[0, positive_column])
np.testing.assert_allclose(before_saving, after_loading, rtol=0, atol=1e-12)
print({"before_saving": before_saving, "after_loading": after_loading,
       "threshold": loaded["metadata"]["threshold"],
       "decision": int(after_loading >= loaded["metadata"]["threshold"])})

5. Enviar el mismo cliente a la API

client.post envía un objeto JSON a la ruta real /predict mediante el cliente de prueba en el mismo proceso de FastAPI. FastAPI valida el cuerpo, construye la entrada del modelo, carga el artefacto configurado y devuelve una respuesta tipada. .json() decodifica esa respuesta en valores de Python. Las aserciones comparan la probabilidad de la API, el thresholdguardado y la decisión con las rutas directas, en memoria y tras cargar el artefacto.

Consulte la referencia oficial de Guía de FastAPI sobre el cuerpo de la solicitud explica cómo los modelos de Pydantic definen los cuerpos de las solicitudes JSON.

Python · ejecutar en el cuaderno
with local_prediction_client(artifact_path) as client:
    response = client.post("/predict", json=customer)
    assert response.status_code == 200
    result = response.json()
np.testing.assert_allclose(result["churn_probability"], before_saving, rtol=0, atol=1e-12)
assert result["threshold"] == threshold
assert result["prediction"] == int(before_saving >= threshold)
print("HTTP status:", response.status_code)
print(json.dumps(result, indent=2))
print("Parity verified: before saving = after loading = API probability.")

6. Rechazar una solicitud no válida

El modelo de entrada de la API exige los cuatro campos, prohíbe los campos no declarados, comprueba los intervalos numéricos y restringe contract a tres valores documentados. El valor quarterly no pertenece a esa enumeración, así que FastAPI devuelve el estado 422 antes de puntuar con el modelo. Las entradas de software no válidas deben rechazarse en el límite del contrato con una respuesta de validación clara.

La Guía de FastAPI para el manejo de errores describe los errores de validación de solicitudes y el estado 422.

7. Revisar el contrato que se entregará

El proceso carga el artefacto del disco y lo mantiene en caché por ruta. Reemplazar el archivo no vuelve a entrenar el estimador; un proceso existente puede seguir usando el artefacto que tiene en memoria hasta que lo recargue o reinicie. Los metadatos permiten inspeccionar el esquema esperado, el umbral seleccionado, la identidad de los datos y las versiones de dependencias. El hash identifica el archivo de entrenamiento usado, mientras que las versiones ayudan a reconstruir el entorno de serialización; ninguno garantiza un comportamiento idéntico en todas las plataformas o versiones futuras de las bibliotecas.

Campo de la solicitud Valor admitido Motivo de la restricción
tenure_months Entero entre 0 y 120 Coincide con el intervalo modelado y rechaza una antigüedad negativa
monthly_charge Número finito entre 0 y 100 000 Impide valores no finitos y entradas fuera del intervalo
support_calls Entero entre 0 y 10 000 Conserva la semántica de conteo y limita la entrada
contract monthly, annual o two_year Debe coincidir con las categorías admitidas por el contrato del modelo

Una solicitud no válida recibe el estado 422. Si el artefacto no existe o falla las comprobaciones de formato, esquema o probabilidades, /health y /predict /health y /predict devuelven el estado 503. Una respuesta 200 confirma que se puntuó una solicitud admitida; aun así, un cambio en las entradas puede debilitar los supuestos estadísticos. Este servicio didáctico local no implementa autenticación, TLS, controles de privacidad, límites de solicitudes ni supervisión operativa.

Extensión opcional: registrar este mismo artefacto con MLflow

El seguimiento registra los parámetros, las métricas, las etiquetas y los archivos del artefacto de una ejecución para poder inspeccionarla después. Esta celda registra el mismo artefacto guardado, el umbral seleccionado en validación, las métricas de prueba final y el hash de los datos, sin ajustar otro estimador. El URI local de seguimiento SQLite pertenece a este MlflowClient cliente, por lo que la celda no modifica una configuración de seguimiento global del proceso.

Python · ejecutar en el cuaderno
import os
os.environ.setdefault("MLFLOW_DISABLE_TELEMETRY", "true")
from mlflow import MlflowClient
tracking_directory = ROOT / ".verification" / "deployment-tracking"
tracking_directory.mkdir(parents=True, exist_ok=True)
tracking_client = MlflowClient(tracking_uri="sqlite:///" + (tracking_directory / "mlflow.db").as_posix())
experiment_name = "single-artifact-deployment"
experiment = tracking_client.get_experiment_by_name(experiment_name)
experiment_id = (experiment.experiment_id if experiment else
                 tracking_client.create_experiment(experiment_name))
run = tracking_client.create_run(experiment_id)
run_id = run.info.run_id
tracking_client.log_param(run_id, "threshold", threshold)
tracking_client.set_tag(run_id, "data_sha256", metadata["data_sha256"])
for name, value in metrics.items():
    tracking_client.log_metric(run_id, name, value)
tracking_client.log_artifact(run_id, str(artifact_path))
tracking_client.set_terminated(run_id)
print("Tracked the same saved artifact in run:", run_id)

Interpretar las llamadas de seguimiento como registro

El cliente busca un experimento con nombre o lo crea, inicia una ejecución y registra el threshold como parámetro, el hash del CSV como etiqueta, las métricas finales como métricas y el joblib como archivo del artefacto. set_terminated cierra la ejecución. La base SQLite y el identificador de ejecución permiten inspeccionarla localmente; el seguimiento no modifica el modelo ni el threshold.

Extensión opcional: ejecutar un servidor independiente y usar Docker

El README de despliegue explica cómo iniciar Uvicorn y construir la imagen de Docker. El entrenador de línea de comandos genera su propio artefacto con el umbral predeterminado documentado threshold; se trata de una ejecución de entrenamiento independiente. Para servir exactamente el pipeline ajustado y el umbral elegido en validación en este cuaderno, configure MODEL_PATH con la ruta guardada que se imprimió antes y, luego, ejecute python -m uvicorn course_ml.app:app --host 127.0.0.1 --port 8001. El proceso lee la ruta de su entorno y almacena en caché el artefacto tras cargarlo.

Qué resuelve el ayudante del cuaderno

course_ml.teaching.local_prediction_client configura temporalmente MODEL_PATH, vacía la caché de artefactos de la API y abre TestClient, y después restaura el entorno y la caché previos dentro de un bloque finally . Así, las demostraciones secuenciales usan el archivo elegido incluso al volver a ejecutar el cuaderno. Un servidor real debe recibir la ruta del modelo antes de iniciarse; los cambios temporales de entorno del ayudante no están pensados para el enrutamiento concurrente.

La función guardada es reproducible si se cuenta con un artefacto confiable, un entorno compatible de Python y bibliotecas, el esquema ordenado y la misma implementación de preprocesamiento. El contrato de la API comprueba si puede aceptar y puntuar un registro.
