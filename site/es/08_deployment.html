Lección 08 — De un modelo estadístico a un servicio de predicción

Esta lección convierte un clasificador binario en una unidad de despliegue pequeña e inspeccionable. Usa una tabla sintética de bajas de clientes con las variables tenure_months, monthly_charge, support_calls, y contract, y el objetivo binario churn. El objeto ajustado es un Pipeline: la estandarización numérica, la codificación one-hot de categorías y la regresión logística viajan juntas en un solo artefacto.

Comience con el cuaderno principal

Abre lesson.ipynb y siga un artefacto desde el ajuste y el umbral de validación hasta la evaluación final, el guardado, la carga y la respuesta de la API. El cuaderno comprueba que todas las rutas de inferencia devuelvan la misma probabilidad y política guardada. No hace falta iniciar un servicio en segundo plano. El artefacto queda en .verification/deployment-core para inspeccionarlo.

MLflow y Docker son extensiones opcionales. El flujo de línea de comandos que sigue es un entrenamiento independiente con umbral predeterminado de 0,5; no reutiliza automáticamente la política seleccionada en el cuaderno. Para servir el artefacto del cuaderno, configure MODEL_PATH con la ruta guardada que se imprimió.

Flujo opcional de línea de comandos y servidor

Desde la raíz del repositorio, entrene y guarde el modelo con:

python -m course_ml.train --data data/churn.csv --output artifacts/churn.joblib

El comando reserva un conjunto estratificado de prueba, informa exactitud, precisión, exhaustividad, F1 y AUC ROC, y guarda el pipeline con sus metadatos. Estos registran el esquema de variables, el significado del objetivo, el umbral, los tamaños de las particiones, la semilla aleatoria y las métricas de prueba. --threshold 0.35 cambia la regla que convierte una probabilidad en una etiqueta de clase. No vuelve a ajustar el modelo de probabilidades. El umbral predeterminado es 0,5.

Para registrar un experimento local, añada --track. MLflow está incluido en el entorno del curso:

python -m course_ml.train --data data/churn.csv --output artifacts/churn.joblib --track

MLflow guarda los parámetros de la ejecución y las métricas del conjunto de prueba en una base de datos SQLite local llamada mlflow.db; los archivos del modelo y otros artefactos van a su almacén local de artefactos. Configure MLFLOW_TRACKING_URI para usar otro almacén de seguimiento. Cada ejecución también registra el hash SHA-256 del archivo de datos, las versiones de Python y de las bibliotecas numéricas, los parámetros de regresión logística, la firma del modelo y un ejemplo de entrada. El hash identifica los bytes exactos del CSV utilizado para entrenar. El seguimiento facilita comparar experimentos, pero no demuestra que el modelo sea estadísticamente sólido. Para reproducir un resultado, conserve también la revisión del código fuente.

Consulte la base local de experimentos con:

mlflow ui --backend-store-uri sqlite:///mlflow.db --host 127.0.0.1

La interfaz escucha en el puerto 5000 de forma predeterminada. Vincularla a 127.0.0.1 mantiene esta interfaz didáctica en el equipo local.

El servicio FastAPI lee MODEL_PATH, cuyo valor predeterminado es artifacts/churn.joblib. Para servir el modelo localmente, primero entrénelo e inicie Uvicorn:

MODEL_PATH=artifacts/churn.joblib python -m uvicorn course_ml.app:app --reload --port 8001

En PowerShell, asigne el valor a la variable del shell actual y ejecute Uvicorn como módulo:

$env:MODEL_PATH = "artifacts/churn.joblib"
python -m uvicorn course_ml.app:app --reload --port 8001

GET /health comprueba si se puede cargar el modelo configurado. POST /predict acepta un objeto JSON con los cuatro campos de variables y devuelve la probabilidad de baja, el umbral guardado y la decisión resultante 0/1. La aplicación nunca ajusta un modelo mientras atiende solicitudes.

Puede probar la API sin abrir un puerto de red:

from fastapi.testclient import TestClient
from course_ml.app import app

client = TestClient(app)
client.get("/health").json()
client.post("/predict", json={
    "tenure_months": 8,
    "monthly_charge": 92.0,
    "support_calls": 4,
    "contract": "monthly",
}).json()

Decisiones estadísticas y limitaciones

Para un vector de características \(x\), la regresión logística modela \(p(x)=\Pr(Y=1\mid X=x)=\sigma(\beta_0+\beta^T z(x))\), donde \(z\) es la transformación de preprocesamiento ajustada y \(\sigma(t)=(1+e^{-t})^{-1}\). La estandarización pone las coordenadas numéricas en escalas comparables. La codificación one-hot representa las categorías de contrato sin suponer que el orden monthly < annual < two_year constituya una distancia numérica. Toda la transformación se ajusta con el subconjunto de entrenamiento, de modo que los ejemplos reservados no influyen en las medias, varianzas ni categorías codificadas.

La decisión de clase predeterminada es \(\hat y=1\{p(x)\geq \tau\}\), con \(\tau=0.5\). El umbral es una decisión de política: reducirlo suele aumentar las clasificaciones positivas y la exhaustividad, aunque puede reducir la precisión. Elija un umbral de producción con datos de validación y según el coste de falsos positivos y falsos negativos. La regresión logística se ajusta sin ponderar las clases, por lo que sus probabilidades no se desplazan mediante una corrección por pesos de clase; esto por sí solo no garantiza calibración. Las métricas del conjunto reservado son estimaciones didácticas, no garantías para el tráfico futuro. Los datos sintéticos codifican una relación artificial sencilla y no describen el comportamiento real de clientes.

Diferencias entre entrenamiento y servicio

La API usa el mismo pipeline de preprocesamiento serializado que el entrenamiento, lo que evita discrepancias comunes, como escalar con unas medias en el cuaderno y con otras en el servicio. Las comprobaciones del esquema también rechazan columnas de entrenamiento ausentes o inesperadas; la validación de solicitudes limita los intervalos de las variables y las etiquetas de contrato. Estas medidas no detectan todos los cambios. Supervise las distribuciones de variables, los valores faltantes, las tasas de predicción y los resultados que lleguen más adelante. Compare las entradas reales con la población de entrenamiento y vuelva a entrenar solo después de investigar el cambio y la calidad de las etiquetas.

El cambio de covariables supone que cambia la distribución de características \(P(X)\), mientras la relación condicional \(P(Y\mid X)\) permanece estable. Bajo ese supuesto, las predicciones aún pueden ser útiles, aunque un cambio grande puede dejar partes de la nueva población poco representadas. Si cambia la relación entre las características y la baja, las correcciones por cambio de covariables no resuelven el problema. Supervisar las entradas puede revelar cambios en la distribución; se necesitan etiquetas de resultados para saber si también cambió la calidad predictiva.

Estimador estadístico y contrato de software

Desde el punto de vista estadístico, un procedimiento de aprendizaje transforma una muestra \(D\) en un conjunto estimado de parámetros \(\hat\theta\), y el modelo ajustado transforma un vector de características en una probabilidad. En software, el servicio tiene un contrato aparte: qué campos debe contener la solicitud, sus tipos y valores permitidos, qué incluye la respuesta y qué errores puede esperar quien llama. Un modelo matemáticamente válido puede ser inutilizable si esas reglas de entrada y salida no están claras o cambian sin aviso.

Al cargar un artefacto guardado, las predicciones para las mismas entradas deberían conservarse en un entorno de software compatible; la prueba de ida y vuelta comprueba esa propiedad. Reproducir un ajuste exige más. También requiere los mismos bytes de datos, reglas de preprocesamiento y partición, semillas aleatorias, versiones de paquetes y comportamiento numérico compatible. Aun así, compare los resultados de punto flotante con una tolerancia cuando cambien las plataformas o las bibliotecas numéricas.

Seguridad y límites operativos

La API acepta un pequeño registro JSON validado y no implementa autenticación, autorización, límites de solicitudes, configuración TLS, registros de auditoría ni controles de privacidad. Es un servicio didáctico local: no debe recibir datos reales de clientes ni exponerse públicamente tal cual. joblib usa la semántica de pickle de Python: cargue artefactos solo de fuentes confiables, pues un archivo malicioso puede ejecutar código. En un despliegue real, fije las versiones de dependencias, autentique a quienes llaman al servicio, proteja el transporte y los datos almacenados, limite las solicitudes y defina la supervisión, la reversión y la procedencia de los artefactos.

Siga la lección

Ejecuta lesson.ipynb de principio a fin. Siga el mismo pipeline ajustado y el umbral seleccionado en validación durante la evaluación final, la serialización, la carga y la solicitud a /predict . Antes de cada bloque de código, anticipe qué estado lee o modifica; luego compare el resultado del modelo en memoria, el artefacto cargado y la respuesta de la API. El cuaderno localiza la raíz del repositorio y guarda un artefacto con nombre único bajo .verification/deployment-core, así que no sobrescribe el modelo de línea de comandos. Su TestClient permite probar la ruta sin iniciar un servidor que bloquee la sesión.

Para construir el contenedor desde la raíz del repositorio y publicar la API solo en el equipo local:

docker build -t churn-course-api .
docker run --rm -p 127.0.0.1:8001:8000 churn-course-api

El Dockerfile de la raíz instala el paquete del curso, entrena con el archivo sintético incluido data/churn.csve inicia Uvicorn. Compruebe http://127.0.0.1:8001/health y envíe solicitudes de predicción a http://127.0.0.1:8001/predict. El contenedor escucha en todas las interfaces internamente; la asignación del puerto del host mostrada arriba lo expone solo mediante la interfaz de loopback.
